Ring++ 2.0.8 -- `rnxc resident`: one running program that takes new code, and a socket for its own request loop.

**A program that stays, and takes new code while it runs.** `rnxc resident a.ring b.ring ...` holds ONE program and admits
each file into it: compiled on top of everything admitted before it, admitted or refused WHOLE, and an admitted file's top
level runs as a loaded file's does. Every value the program holds is kept from one admission to the next.

- From inside the running program, `admitfile(cPath)` and `admitcode(cName, cSource)` admit a file or a string and answer 1.
  A refusal raises, catchably, with the reason and the first refused statement, and leaves the program as it was.
- `replacefile` and `replacecode` (`--replace <file>` on the command line) replace a function or a class the program holds:
  every call from then on runs the new body, and a frame already inside the old body finishes it. Objects that exist answer
  with the replaced class's methods, and a class may gain attributes -- each object takes them at its first use, with the
  starting value the class declares.
- `releasefile` and `releasecode` (`--release <name>`) undo the program's last admission: its functions, globals and
  constants are gone, and the program is what it was before it.
- A class may arrive in any admission, from a parent admitted earlier; a `new K` compiled before `K` existed finds it once
  an admission defines it, as Ring finds a class by name; and a call to a function no file defines yet reaches it once one
  does.

What it refuses, and says: a file holding a statement that does not compile; a function or a class defined again without
the replace verbs (Ring refuses both, C22 and C26); a replacement that changes a function's parameter count or the
attributes a class's objects already hold; and a release of an admission that brought a class or a lambda, which an
object or a closure could outlive. Ring has no counterpart for replacing or releasing code, so those answers are judged
by this project's own transcripts; every line an admitted file prints that Ring would print is compared with Ring running
the same files in order.

What it costs: an admission takes about a millisecond in a program holding Softanza's whole library (49,000 functions).
A program run with `rnxc <file>` pays nothing measured. A resident program keeps every function's parameters boxed, since
later code may call them with anything -- a few percent on integer-heavy calls (`Fib(30)` 81 -> 82 ms).

**A socket for a program that holds its own request loop.** Eight functions inside `rnxc` -- no library, no DLL:
`rpp_http_listen(nPort)` on 127.0.0.1, `rpp_http_next()` to wait for the next request, `rpp_http_method()`,
`rpp_http_path()`, `rpp_http_query()`, `rpp_http_header(cName)`, `rpp_http_body()`, and
`rpp_http_reply(nStatus, cType, cBody)`. One request at a time, one connection each; routing and every decision stay in the
program. Under `rnxc resident` a deployment can be a request: the program admits the new code and answers. Sequential
requests, a connection each, are answered in under 0.2 ms here.

**A string function handed a number raises, as on Ring** (F-147). `substr`, `strcmp`, `ascii` and their kind given a number
where Ring wants a string ended the process (exit 3); they raise "Bad parameter type!", catchably -- 73 calls measured on
Ring 1.27 first, every one alike. `substr` with four arguments (a replacement ignoring case when the fourth is 1) works; it
answered "Calling Function without definition". `ascii(5)` raises instead of answering 5.

Everything in 2.0.7 is here unchanged. The gate passes, and the 175 probe programs run byte for byte as Ring runs them on
Windows, and 176 on Linux. Each archive was unpacked into an empty folder and run in a clean environment on Windows and on
Linux, from a third folder, with an empty cache.

Unpack anywhere -- the Windows zip, or on Linux `tar -xzf ringpp-linux-x64.tar.gz` -- and run `bin/rnxc program.ring`, or
`bin/rnxc resident a.ring b.ring` to run files as one program that can take more.

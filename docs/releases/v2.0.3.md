Ring++ 2.0.3 -- a function too large for the register window compiles now.

**Locals share registers when one apiece does not fit.** An instruction names a register in a byte, so a function had
at most 200; Softanza's `stzDiagram.ToCanvasXT` has 631 locals in 3,909 lines, and Ring++ refused it, so every diagram
drawn to a canvas stopped with R24. In a function whose locals do not fit, locals whose uses do not overlap now share a
register, and each is cleared where its own use begins, so reading one before it is assigned is still Ring's R24.
Every other function compiles to exactly the code it did before. `ToCanvasXT` needs 86 registers, and Softanza's base
library now compiles whole: 118,640 of 118,640 statements.

**The figure.** Of the 13,008 checks Softanza's tests pass on Ring, Ring++ 2.0.3 passes **12,924 on Windows (99.4%)**,
against Softanza as of 4 October 2026: 61 more than 2.0.2, the five graphics tests the register window reached. On
Linux it is **12,170 of 12,255 (99.3%)**, measured on 2.0.2; 2.0.3 compiles every function but that one to the same
code. Of the 84 checks not passed on Windows, 81 are in three test files that read a global without its `$` inside a
function, which Ring++ refuses to compile; they are corrected in Softanza since, and pass every check. The other three
measure time. They are listed at https://mayouni.github.io/ringpp/how.html#parity.

Each archive was unpacked into an empty folder and run in a clean environment on Windows and on Linux.

Unpack anywhere -- the Windows zip, or on Linux `tar -xzf ringpp-linux-x64.tar.gz` -- and run `bin/rnxc program.ring`.

Q&A.

Each answer points at the number or the document behind it.

Why exclude Qt specifically? Isn't that arbitrary?

Two reasons, and the business one came first. Qt is dual-licensed — free under LGPL terms with real obligations for how a commercial product links and redistributes it, or a paid commercial licence otherwise. For software shipped to customers, that's a real risk, decided against before Ring++ existed. The technical reason came later, and confirmed the call: bundling the one library static analysis can name (ringqt.dll) produces a package that reports nothing missing and then crashes with no diagnostic at all, because that one DLL itself depends on ~75 further Qt libraries no .ring source ever names. Measured, not assumed — the walkthrough.

What does "dependency-free" actually mean, precisely?

The library needs nothing but stock Ring — no extension, no DLL, no toolchain. The CLI needs nothing but itself — no C compiler, ever, on the user's machine. Two things are compiled into the CLI at build time, and are named on the front page rather than hidden: Ring's own grammar (tree-sitter-ring) and Zig's toolchain, which produces the binary. Nothing is vendored at a user's install time.

Does ringpp build replace ring2exe?

No, and it is not trying to. ring2exe writes a .c file and shells out to Visual C++, GCC or Clang — a real C compiler on the user's machine. ringpp build reaches a runnable pair with none of them, by attaching a prebuilt runtime stub to Ring's own bytecode instead. Different mechanism, and it does not touch ring2exe or replace it for cases that need a true single self-contained executable — the artefact here is a small pair of files, stated plainly on the build page.

Is the packaged output really one file?

No — and an earlier draft of this project's own design doc said so before it was checked. Ring's runtime does not look for a same-named bytecode file when run with no arguments, and appending bytecode to the executable does nothing either — both measured directly before anything was built around the assumption. What ships is a small pair: name.exe and name.ringo, invoked together.

Why does the checker refuse instead of just reporting "probably fine"?

Because a checker's only asset is that it is never wrong about correct code. A program whose load chain could not be followed gets NO VERDICT, never a false "clean" — the same failure this project found and fixed twice in its own measurement tooling. Details on the static analysis page.

What about the sibling projects — RingScript and RingServ?

Each stands alone; neither depends on Ring++ or is depended on by it. Running Ring++'s own tools against both, read-only, found zero dormant bugs — a result in itself — plus a concrete RppBuffer candidate in one, a hand-built RppIndexed equivalent independently converged on in the other, and two mistakes in Ring++'s own published claims, caught along the way and corrected. A third sibling, MicroRing — Ring on the device — is upcoming.

Where do I report a bug, or ask something not here?

GitHub issues. Findings about Ring itself go to the Ring Google Group, posted by the maintainer after review — never a pull request against ring-lang/ring by default.

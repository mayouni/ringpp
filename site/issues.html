Ring's issues that Ring++ solves

Each issue below is a small Ring program, run on official Ring 1.27 and on Ring++ (16 October 2026). You read the program first, then what each runtime printed. Nothing here is a promise: it is what the two printed.

Programs that die

An object taken from a list ends the program, with no message

SolvedF-100C-24

Ring 1.27 Adding two objects through their operator method works -- unless the right one comes from a list: then the program stops, exit code 1, no error printed, and no try can catch it.

Ring++ The operator is called, and the program goes on.

# Two prices: one in a variable, one inside a list
oPrice  = new Money { nAmount = 10 }
aPrices = [ new Money { nAmount = 5 } ]

# Add them: the class tells Ring how to add two Money objects
oTotal = oPrice + aPrices[1]
? oTotal.nAmount
#--> Ring 1.27: nothing at all -- the program ends here, exit code 1,
#    with no error message, and no try/catch can stop it
#--> Ring++: 15

? "done"

class Money
	nAmount = 0

	func operator cOp, oOther
		oSum = new Money
		oSum.nAmount = nAmount + oOther.nAmount
		return oSum
Ring 1.27 printed
(nothing)
(the program stops, exit code 1)
Ring++ printed
15
done

Empty catch blocks fill the stack until the program dies

SolvedF-16

Ring 1.27 Each empty catch leaves one slot on the VM's stack. A loop that expects failures dies with Stack Overflow.

Ring++ Nothing is left behind; the loop runs to the end.

# Try something that fails, 3,000 times, and ignore the failure
for nTry = 1 to 3000
	try
		raise("a failure we expect")
	catch
		# nothing to do: the failure is expected
	done
next

? "3,000 failures handled"
#--> Ring 1.27: Error (R4) : Stack Overflow -- every empty catch
#    leaves one slot behind, until there is no room left
#--> Ring++: 3,000 failures handled
Ring 1.27 printed
Line 2 Error (R4) : Stack Overflow
(the program stops, exit code 1)
Ring++ printed
3,000 failures handled

Wrong answers, given silently

Reading a missing key adds it

SolvedC-13F-49

Ring 1.27 Asking a hash list for a key it does not have inserts that key. A read changes the data it reads.

Ring++ A read never writes.

# A hash list with two entries
aHash = [ :a = 1, :b = 2 ]

# Read an entry that does not exist
nValue = aHash[:c]

# How many entries are there now?
? len(aHash)
#--> Ring 1.27: 3 -- reading :c silently ADDED it to the list
#--> Ring++: 2 -- a read never writes
Ring 1.27 printed
3
Ring++ printed
2

A method overwrites the program's variable

SolvedC-2

Ring 1.27 A method that assigns a name the program also uses writes the program's variable, silently. Softanza spells its own variables _name_ at 175,797 places to avoid it.

Ring++ A method's variables are its own. A global is written $name.

# A variable of the program
cName = "Mansour"

# An object whose method uses a variable with the same name
oGreeter = new Greeter
oGreeter.Greet()

# Is the program's variable unchanged?
? cName
#--> Ring 1.27: a visitor -- the method silently overwrote it
#--> Ring++: Mansour -- a method's variables are its own

class Greeter
	def Greet()
		cName = "a visitor"

a visitor
Ring++ printed
Mansour

Speed

Three choices in Ring's design cost it the most: strings copied at every call, lists that are linked, and methods found by name at every call. Ring++ replaces all three. The same programs, on the same machine, minima of three runs, every answer checked equal:

What Ring++ keeps from Ring, for now

Some of Ring's behaviours are kept on purpose, so that existing programs keep their meaning: a list printed one item per line, a named argument that arrives as a two-element list, decimals() as a setting for the whole program, a string measured in bytes. They are not solved, so they are not listed above. They are decisions, explained below, and the next language, Haro, is where they change.

Every decision, explained

Where Ring++ answers differently from Ring, it is never by accident. Each difference is a decision, taken for one defect at a time and written down with what it costs. There are four kinds.

Keep Ring's answer, so existing programs keep their meaning, even where Ring's choice is questionable. decimals(2) still changes every number the program prints from then on. A bare name at the top level is still a global. A load that names a missing file still stops the program before it starts, exactly as on Ring.

Fix it silently, where no correct program can notice. Reading aHash[:key] no longer inserts the key. An object taken from a list no longer ends the program when it meets an operator. Leaving a try through return also leaves its handler, from a function as from a method.

Refuse, with a rule, where Ring's behaviour is a trap. The program is refused before it runs, and rnxc check names every place the rule applies: a loop variable read after its loop, a numeric for whose bound changes while it runs.

Drop it, and say so, for what only Ring's own programs use and Softanza never does: renaming keywords, packages, raw memory pointers. Each is refused by name rather than half-built.

All 31 decisions are on record, each with its reasons and its cost, in the corrections register.

Every finding, explained

The findings are what Ring's VM was measured to do: 126 of them, each from a program that ran. They fall into four families.

Costs the source does not show. A string passed to a function is copied, every time. A loop written for i = 1 to len(s) measures the string again at every turn, which makes it quadratic. How fast a list is read depends on how it was built and on where it was read last. On identical programs, Ring measured 9 to 16 times behind Lua.

Traps. N and n are the same variable. Every func written after the first class of a file becomes a method of that class. A string has no escapes: "\n" is two characters. char(300) is char(44), silently.

Rules that Ring++ had to learn, to run Ring's programs as they are. :Name = value is a two-element list. Ring calls Main() by itself after the top level. Every operator on an object calls its operator() method. eval runs in the scope of the function that calls it.

Ring's own failures. memcpy() ending the process on a zero byte; empty catch blocks filling the stack; an object from a list ending a program without a message; the Linux build crashing as it exits.

All 126, each with the program that shows it, are in the findings.

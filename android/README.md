# The Android demo

One Ring program, packaged as an installable Android app by the CLI itself:

```
ringpp build android/app.ring --target android \
    --label "Ring++ on Android" --package org.softanza.ringpp.demo
```

That is the whole recipe. `app.ring` is the only hand-written file here —
the manifest, the Java activity, the dex and the APK are all generated by
`ringpp build`, which is why they are not checked in.

`ringpp-demo.apk` is the output of that command, kept in the repository so
the claim can be checked without building anything:

```
adb install -r android/ringpp-demo.apk
adb shell am start -n org.softanza.ringpp.demo/.MainActivity
```

`screenshot.png` is that APK running on an Infinix X6817 — `arm64-v8a`,
Android 12 (API 31).

## What it needs, and what it does not

Android is the one `--target` that needs a toolchain: an Android SDK and a
JDK 17+, because only Google's `aapt2` writes Android's binary manifest
format. Point at them with `--sdk` and `--jdk`, or set `ANDROID_HOME` and
`JAVA_HOME`. Missing either, the command says which one and refuses.

It needs **no NDK, no Qt, no Qt Creator, no Gradle, no JNI and no C
compiler**. The VM inside the APK is byte-identical to the `linux-arm64`
stub every other `ringpp build` ships — it is not a port, it is the same
file under the `lib*.so` name Android insists on ([F-36](../docs/FINDINGS.md)).

## Why there is no build script here any more

There was one: a 160-line Python script that drove `aapt2 → javac → d8 →
zipalign → apksigner` by hand. It proved the chain, and then everything it
knew moved into `src/android.zig` where the CLI could use it. Two
implementations of the same packaging would have drifted, and the one the
users get is the one that has to be right.

Its disappearance also exposed a defect it had been hiding. The script ran
Ring with `cwd` set to this directory, so the demo program's own
`report.txt` landed here and looked like build scratch. Run from the
repository root instead, the same file appeared where nothing claimed to
write one — which is how it was noticed that `ring -go` **compiles and then
runs** the program, and that every `ringpp build` had been executing what
it packaged. See [F-37](../docs/FINDINGS.md).
